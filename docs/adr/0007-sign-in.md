# 0007. Вход через систему вуза

Дата: 2026-11-12. Статус: принято.

## Решение

Студенты и преподаватели входят той учётной записью, которую им уже выдал вуз (Microsoft, Google, Keycloak и любой другой OIDC провайдер). Lodestar не хранит пароли. Вход по почте для пилота появится отдельной частью.

## Как устроено

- Способы входа вуза лежат в `core.identity_providers`. Секрет клиента зашифрован ключом `LODESTAR_SECRET_KEY` (AES-GCM), в базе его прочитать нельзя.
- Приложение открывает `GET /v1/auth/{вуз}/{способ}/login` со своим PKCE `code_challenge`. Сервер сам проходит Authorization Code + PKCE с провайдером, проверяет ID token и nonce, создаёт или обновляет пользователя.
- Приложение получает одноразовый код на свой адрес возврата (только из списка `LODESTAR_APP_REDIRECTS`) и меняет его на токены через `POST /v1/auth/token`, доказывая `code_verifier`.
- Токены случайные, в базе хранится только их SHA-256. Внутри токена записан id вуза, поэтому сервер сразу знает, в каком вузе искать сессию, и правило из [0006](0006-tenant-isolation.md) работает и здесь.
- Токен доступа живёт 15 минут, токен обновления 60 дней (оба настраиваются). При каждом обновлении выдаётся новая пара. Повторное использование старого токена обновления считается кражей: сессия закрывается.
- Каждая сессия привязана к устройству. Пользователь видит свои устройства и может выйти на любом из них.

## Почему

Вузу не нужно заводить людям новые пароли, а Lodestar не становится местом утечки паролей. Короткий токен доступа и проверяемые токены обновления ограничивают вред от украденного устройства.

## Отвергнуто

- JWT для доступа: нельзя мгновенно отозвать, а проверка сессии в базе дешёвая.
- Вход провайдера прямо из приложения: секрет клиента пришлось бы держать в приложении.
